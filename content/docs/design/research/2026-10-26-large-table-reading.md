> [!NOTE] Historical research; see the 1.4.0 decision
> Owner: OINK maintainers. Research date: 2026-10-26, Asia/Shanghai. This study informed the table-reading design in OINK 1.4.0. The [accepted decision](/docs/design/decisions/large-table-reading/) and [table guide](/docs/components/table/) describe the released behavior and supersede the entrance and scope recommendations below. This record preserves the evidence and alternatives considered at the time.

**An explicit Read table action opening a large native dialog is the strongest candidate for further evaluation.** It gives desktop tables more room while preserving text size, original table semantics, and a short return path. Inline widening remains sufficient for many tables; the measured package excerpt already fits that mode on desktop. On a 390px viewport, the dialog adds only 16px of width, so it does not eliminate horizontal scrolling. Five documentation frameworks support the simpler baseline of native tables and overflow handling; richer libraries supply data operations at additional integration cost. The external concept supports a reading direction, not release acceptance, accessibility certification, or a decision to ship TSV.

## Evidence separates layout, content, and release state {#method}

The public tag snapshot was [v1.3.2](https://github.com/pgsty/oink/releases/tag/v1.3.2), with reported tag ref `68cfbbdc177064e2c28277c09c385d78e5363ffd`. Research began at theme HEAD `7bc8658bc1be13ef0ad3050b9d9f6862f8f1f65f` and site HEAD `99751179eefada3fa7a91318c792ddac46d7e6bf`, both dirty. The site pinned v1.3.2. These identities describe the research inputs, not a clean commit containing the experiment or hosted production output. The short `.wide` alias was part of that local experiment; it is included in OINK 1.4.0 as described by the current [component contract](/docs/design/components/#steps-cards-fields-and-tables).

The local owners inspected were `oink/layouts/_partials/content/table-render.html`, `table-body.html`, `assets/scss/td/_content.scss`, `_table.scss`, the preset/font tokens, and the surface coordinator. `.wide`/`.td-table--wide` control intrinsic sizing and token wrapping; `.full-width` reaches the available article canvas. `.matrix` supplies first-column row headers and bounded two-axis scrolling, with existing sticky header/first-column CSS. That CSS gives each header `top:0`, without accumulated multirow offsets or a mobile first-column width guard. `.fields` emits a definition list. None of these meanings establishes a fullscreen reader. Ordinary captions belong inside the table; numbered Book captions belong to the outer figure. ([Table guide](/docs/components/table/), [output contract](/docs/design/architecture/#outputs-and-runtime).)

Source values are comparison content, not independently verified package or OS support claims. The separate 616-row extension catalog was not performance-tested.

These examples distinguish **many columns**, **many rows**, **long cells**, and **complex headers**. Wider viewports primarily help the first; sticky orientation helps the second; wrapping helps the third. Multirow and merged headers need explicit associations and offset handling, not just more width. The selected prototype tables all have one header row and no merges, so the last category remains a design and acceptance question. GFM pipe-table syntax itself defines a header row and inline cell content, not a data-grid interface. ([GFM tables](https://github.github.com/gfm/#tables-extension-), [WAI multilevel headers](https://www.w3.org/WAI/tutorials/tables/multi-level/).)

## Richer libraries add data operations and ownership {#components}

Current versions matter. **DataTables 3.1.4 does not require jQuery**, unlike earlier generations. **TanStack Table 9.3.1 is not v8**: it uses `constructTable`, feature selection, and Store reactivity. Package evidence takes precedence over older assumptions or floating manuals. ([DataTables v3 dependency boundary](https://datatables.net/manual/core/jquery), [TanStack v9 announcement](https://tanstack.com/blog/announcing-tanstack-table-v9).)

| Component | Fit and available operations | Integration and maintenance boundary |
| --- | --- | --- |
| DataTables 3.1.4, released 2026-10-13; MIT, no required core runtime dependency | Enhances HTML tables using an internal data model; core sorting/search/paging; optional Buttons, FixedColumns, FixedHeader, Scroller | Closest candidate for later systematic table operations. Scrolling can copy/move headers; semantics still need verification. Supports complex `thead`, not `tbody` spans. ([Release](https://github.com/tabulator-tables/tabulator/releases/tag/6.7.1), [package](https://registry.npmjs.org/tabulator-tables/6.7.1), [importer](https://github.com/tabulator-tables/tabulator/blob/6.7.1/src/js/modules/HtmlTableImport/HtmlTableImport.js).) |
| TanStack Table core 9.3.1, released 2026-10-12; MIT, `@tanstack/store ^0.11.2` | Headless sorting/filtering/pinning/selection/spanning logic; vanilla integration is supported | Maintainer owns HTML import, rendering, controls, styles, focus, export and dialog. ([Metadata](https://registry.npmjs.org/@tanstack/table-core), [fixed package](https://registry.npmjs.org/@tanstack/table-core/-/table-core-9.3.1.tgz), [vanilla guide](https://tanstack.com/table/latest/docs/framework/vanilla/quick-start).) |

DataTables' FixedHeader/FixedColumns are optional extensions. Scroller requires equal-height rows, a poor untested fit for wrapped technical descriptions. Tabulator emits ARIA grid structures; its editable-cell navigation cannot establish read-only accessibility. TanStack's spanning API does not provide lossless import of arbitrary HTML merges. None of the inspected packages establishes a complete official fullscreen reading control. Tabulator's `printFullscreen` belongs to printing. These are bounded findings, not claims about all community integrations. ([Scroller](https://datatables.net/manual/extensions/scroller/), [Tabulator navigation](https://www.tabulator.info/docs/6.x/navigation/), [Print source](https://github.com/tabulator-tables/tabulator/blob/6.7.1/src/js/modules/Print/Print.js), [TanStack spanning guide](https://tanstack.com/table/latest/docs/framework/react/guide/cell-spanning).)

Copy defaults also differ. Buttons 4.1.2 exports display data with current order/filter rules and span placeholders; its copy path does not enable formula escaping by default. Tabulator 6.7.1 joins cell values with tabs/newlines without general quoting or formula neutralization in that serializer. Neither behavior should silently become OINK's copy contract. Tablesort 5.7.1 is a narrow MIT, dependency-free sorting comparison: it preserves table rows and handles Enter on headers, but provides no reader/filter/export layer. Material's recipe uses 5.3.0; the newer size and keyboard findings do not apply to that older recipe. ([Buttons source](https://github.com/DataTables/Dist-DataTables-Buttons/blob/4.1.2/js/dataTables.buttons.js), [Tabulator Clipboard](https://github.com/tabulator-tables/tabulator/blob/6.7.1/src/js/modules/Clipboard/Clipboard.js), [Tablesort source](https://github.com/tristen/tablesort/blob/5.7.1/src/tablesort.js).)

## The concept widens desktops much more than phones {#prototype}

The external prototype used a real sibling documentation-site Hugo build with an external content mount, never `tests/site/`. PGEXT-specific shortcodes became explicit labels/links; parameter fragments resolved to their source URLs; support icons received “Supported” text alternatives. Added captions and `.wide` were experimental adaptations. Every reading mode reused the same generated table data. The build used the sibling replacement with both workspaces disabled and external destination/cache/resource directories; the accepted LibSass warning remained visible.

The comparison shell was custom: a 230px rail, 40px desktop main gutters, 68ch normal measure, and 1130px available canvas. Real generated OINK CSS/fonts supplied table and preset styling. It did not load the complete shell runtime or surface coordinator. A separate generated table-guide reference measured a 770px desktop/358px mobile viewport; therefore the concept's narrower baseline is not a measurement of every OINK article.

| --- | ---: | ---: | ---: | ---: |
| Desktop Paper/Terminal | 652.80px | 1130px | 1358px | 1408px |
| Desktop Slate/Ink | 686.38px | 1130px | 1358px | 1408px |
| Mobile, all four presets | 358px | 358px | 374px | 374px |

These are local `qa.json` measurements at 1440×1000 and 390×844, DPR 1; light/dark geometry matched within each preset. Text remained **16px**, code **14px** throughout, preserving existing sizes rather than defining a new minimum. Mobile intrinsic table widths remained about 969–1009px. Desktop inline widening already fits the six-column excerpt; the dialog chiefly adds bounded height, persistent controls, and isolation from prose. Its desktop visible table height was 847.20px, versus 897.20px in page mode; mobile dialog heights ranged 711.02–741.20px as controls wrapped. A long inline table's total content height is not an equivalent visible-height measurement.

Inline widening has the least context-switching cost. The dialog gains desktop space while retaining a direct return to the article. The separate page gains only another 50px on desktop and no mobile width; its stronger case is reloadability and future sharing. Here it is a query-selected concept page, not a Hugo output or accepted route. Returning navigates back and does not preserve original article scroll/focus across reload. None of these modes scales text or invokes the Fullscreen API.

Chromium **151.0.7922.34**, through Playwright 1.62.1, checked **16 preset × color × device combinations**, each with three reading concepts plus baseline. The package sample passed original-node identity, unique IDs, caption/header scopes, loaded styles/fonts, title initial focus, Enter open, Escape/Close return, both Tab boundaries, stable toolbar, separated control/table regions, and page-mode reload. No page overflow was recorded; three additional mobile samples and a 320px Terminal/dark overflow probe extended the scope. A separate inspection preserved link targets and selection and restored inline horizontal scroll to 180px. Screenshot review covered 48 concept captures and contact sheets. **One Paper/light/desktop dialog axe scan reported zero violations; it was not a 16-case accessibility audit.**

The parameter and version samples' first columns occupied 59.3% and 58.3% of the 374px mobile reader. This supports an optional width guard, not a universal percentage. The concept enables no sticky first column. The tested single-row sticky header does not establish multirow offsets. Preset styling remained distinct: Paper's Plex Sans and restrained framing, Slate's Inter and rounded controls, Ink's flat sharp geometry, and Terminal's mono chrome with Plex Sans prose. Existing tokens, not a new palette, supplied both color modes. Ink/Terminal retain their experimental status.

Reproduction uses the retained external builder, source manifest/hashes, generated reference output, QA/inspection JSON, and screenshot set. Serve the saved output to inspect this dated snapshot; rebuilding reads current sibling sources and creates a new manifest. Rebuild with an external content mount, the recorded geometry and unchanged samples, wait for fonts, then capture the 16 combinations and baseline/three concepts with the same computed-size and lifecycle probes. Tools were Hugo 0.168.0+extended+withdeploy, Go 1.27.3 on macOS ARM64, Node 26.12.0, npm 11.20.0, and Python 3.14.8. Artifacts and logs remain outside public content and Git.

Limits are material: Chromium only; mobile/touch emulation, not a physical phone; English comparison controls despite some Chinese cell content; no screen-reader, Firefox/WebKit, forced-colors, 200/400% zoom, safe-area or virtual-keyboard acceptance. No merged headers, external footnotes/ARIA references, nested tabs, coordinator integration, rapid reopen, dynamic updates, or large-row performance were accepted. Static Print/Markdown/RSS reference outputs were inspected, but reader-open native print preview/cancel was not accepted. **Copy TSV is deliberately unavailable.**

## A small reader preserves more than a generic grid {#direction}

The recommended first stage is an explicit, always-visible **Read table** action, a native dialog, and one original-node move/restore lifecycle. Hover-only entry is undiscoverable on touch and keyboard; whole-table click competes with selection, links and scrolling. A visible title/Close control, named scroll region, initial title focus, contained Tab navigation, Escape, and guarded focus/scroll return are substantive requirements. Reuse OINK's surface coordination conventions, not diagram pan/zoom transforms. A near-full dialog is distinct from browser fullscreen, whose standard excludes `<dialog>` as the request target. ([APG dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [Fullscreen Standard](https://fullscreen.spec.whatwg.org/#dom-element-requestfullscreen).)

Retain caption/th/scope/headers and original IDs. Moving avoids clone collisions and divergent state, but inherited styling, outer numbered captions, external ARIA references and footnotes still need explicit handling. Native tables can contain links and sorting buttons without becoming ARIA grids; grids introduce a different focus/navigation obligation. Start with single-row sticky headers; leave complex headers scrollable without stickiness until offsets are validated. Comfortable spacing is default; compact mode changes padding, not font size. Optional first-column pinning must leave useful mobile reading width. Respect reduced motion, browser zoom, touch safe areas and native selection. ([APG table](https://www.w3.org/WAI/ARIA/apg/patterns/table/), [APG grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/), [header semantics](https://html.spec.whatwg.org/multipage/tables.html#header-and-data-cell-semantics).)

Keep `.wide`/`.td-table--wide` layout-only, `.full-width` bounded by article canvas, `.matrix` semantics intact, and `.fields` ineligible. A new opt-in name remains proposed and unimplemented. No-JS content remains readable; Print expands static tables, Markdown retains source, RSS retains its existing static/summary boundary. Reading controls must not leak into those outputs. Sorting/filtering/column pickers require demonstrated tasks and named semantics; virtualization additionally changes browser find, accessible row availability, printing and copy scope. No measured row-count threshold justifies it here.

If TSV follows, recommend copying the **whole eligible table**, including offscreen rows/columns, in author order. Export human text: links become labels, code text remains, hidden controls/decorative glyphs are excluded, and meaningful icons need explicit text equivalents. Initially reject hidden data rows/columns, nested tables, unequal row lengths, multiple header rows, or any DOM `rowSpan`/`colSpan` other than 1, including `rowspan="0"`. Merged tables remain readable; copying must visibly explain the limitation. A future span algorithm must define covered slots, row groups and malformed input, rather than silently flattening. ([HTML table model](https://html.spec.whatwg.org/multipage/tables.html#processing-model-1).)

The proposed profile uses TAB between cells and LF between rows, no final separator, normalizes in-cell tabs/newlines to spaces, and keeps literal quotes without CSV quoting. Code characters survive, but multiline whitespace is normalized. Prefix formula-like cells beginning with `= + - @` after leading whitespace/controls with an apostrophe; label this value-changing risk reduction, not universally safe raw data. Target spreadsheet paste paths remain untested. Await Clipboard API success, announce status politely, and expose selectable normalized text on denial/unavailability. DOM text cannot reconstruct original Markdown or structured source data. ([DOM text](https://dom.spec.whatwg.org/#dom-node-textcontent), [Clipboard 2026-06-24 Working Draft](https://www.w3.org/TR/2026/WD-clipboard-apis-20260624/#clipboard-interface), [OWASP spreadsheet-injection limits](https://community.owasp.org/attacks/CSV_Injection).)

The consequential next decision is whether the dialog improves real comparison tasks enough to justify these integration obligations. A focused native reader leaves data-grid adoption possible later while avoiding an immediate second data model. The original proposal acceptance matrix remains in Git history; the [accepted decision](/docs/design/decisions/large-table-reading/#validation) records the narrower implementation boundary. This dated study alone establishes a candidate, not a release commitment.

## Accepted direction after review {#accepted-direction}

The user selected explicit `{.wide .expand}` composition and a direct corner action, revealed on hover/focus and visible on touch. The above-table toolbar, ellipsis menu, and TSV were excluded from this delivery. The [accepted decision](/docs/design/decisions/large-table-reading/) and [current contract](/docs/design/components/#table-reading) own the resulting behavior. Earlier recommendations and prototype measurements on this page are dated evidence, not the shipped API.
