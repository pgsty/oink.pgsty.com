## 状态与范围 {#status}

本地搜索的形态不变：Hugo 为每种语言写出一份 JSON 索引，读者的浏览器在本地检索。
站点仍然只用 `offline_search: true` 开启，除 Hugo 之外不需要任何工具。
本提案在这个边界之内更换引擎，分三个阶段，各自独立发布。

| 阶段 | 变化 | 状态 |
| ---- | ---- | ---- |
| 1 | 单一的扫描式引擎替换 Lunr 与子串兜底 | 已实现，未发布 |
| 2 | 大索引拆成两份：先加载小的导航索引，正文按体积随后加载 | 已实现，未发布 |
| 3 | 标题以下的定义成为可检索条目 | 已实现，未发布 |

由数据库支撑的搜索是另一份、更晚的设计。[以后的数据库后端](#backend)
只说明本提案为它保留了什么。

## 依据 {#evidence}

以下数字于 2026-11-23 在同一台机器上用 Node 26.13 测得，浏览器中会有出入。

1.5.1 的引擎有两条路径。每个词项都在各字段里做子串匹配；ASCII 单词另外交给
Lunr 做英语词干还原和拼写纠错。第一次遇到这样的单词时，Lunr 要对全站建一遍索引。

| 1.5.1 的问题 | 实测 |
| ------------ | ---- |
| 第一次英文查询会卡 | 两个 `content` 索引为 1.3–1.7 MB 的站点上是 271–410 ms；792 页的 PostgreSQL 手册上是 2.5–3.5 秒，堆内存约 800 MB |
| 长页面上每次查询都慢 | 上述两个站点 27–120 ms，而输入延迟只有 80 ms；手册上最高 890 ms，耗在对整页正文映射摘要位置 |
| 子串匹配 | 搜 `port`，前五条是标题含 "Support" 的页面；435 个页面含这个子串，70 个含这个词 |
| 不加空格的中文查不到 | `数据库连接池超时` 这类查询 16 个里有 7 个没有结果 |
| 词干或纠错命中后没有位置 | `vaccum` 能找到 VACUUM 页面，但没有小节，只显示页面描述 |
| 运算符被丢弃 | `->>` 解析不出词项 |
| 排序不看稀有度和篇幅 | 每个词项同等重要，页面无论多长都算一个单位 |

容量是第二个限制。体量最大的几个在维护的站点都退到了 `summary` 范围，
因为它们的 `content` 索引超出预算；5–10 MB 的全文索引确实存在。
这个问题由第二阶段处理，第一阶段不涉及。

在一个在维护的 163 页站点上，原来的 `content` 索引是 8.1 MB。第二阶段把它发布成
609 KB 的导航索引（gzip 后 123 KB）和 7.5 MB 的正文（gzip 后 2.4 MB），
首批结果只需要前者，不再需要整份索引。在浏览器里，正文到达后重建引擎需要 64 ms，
之后每次查询 3–8 ms。

第三阶段的验证，是把一份实验性的 PostgreSQL 手册转换稿原样构建。每种语言的 7,790 个参数
都成了条目。搜索 `work_mem`、`shared_buffers` 或 `autovacuum_naptime`，打开的是参数自己的条目；
而且只靠导航索引就能做到，不需要先获取任何正文。带上这些条目之后，
导航索引是 1.7 MB（gzip 后 335 KB）。

第一阶段的引擎，在本站的 `content` 索引上（每种语言 166 页、1,443 个小节，约 1.7 MB）：

| 指标 | 1.5.1 | 第一阶段 |
| ---- | ----- | -------- |
| 第一次英文查询 | 198–551 ms | 8–19 ms |
| 查询中位数 | 5.2–8.7 ms | 1.6–2.1 ms |
| 95 分位 | 13.4–19.2 ms | 3.4–4.1 ms |
| 期望页面进入前五，两种范围合计 | 46 条中 43 条 | 46 条中 46 条 |

最后一行统计的是 `summary` 与 `content` 两种范围下指定了页面的 46 条回归查询。
另有两条期望空结果，新旧引擎都通过。新增通过的三条都是不加空格的中文查询。
在 PostgreSQL 手册上，创建引擎需要 65–112 ms，查询平均 10–16 ms，最慢 32 ms，
常驻堆内存 19–32 MB。拼错的单词第一次出现时要多花约 140 ms 收集站点词表。

二元组匹配的原型曾与“jieba 分词加 BM25”在中文手册上对比：35 条中文和中英混排查询里，
两者前十条结果有 82% 相同。这个数字衡量的是一致程度，不是质量。

引擎源码 36.7 KB，gzip 后 11.6 KB。1.5.1 的引擎加 Lunr 是 42.1 KB，gzip 后 12.7 KB。

## 目标与非目标 {#goals}

目标：

- 去掉 Lunr 依赖，以及它在浏览器里建的索引；
- 不带词典，回答不加空格的中文、日文、韩文查询；
- 单词按词边界匹配，标识符和运算符保持字面；
- 排序考虑词项的稀有程度和小节的篇幅；
- 每一处命中都能定位和高亮，包括词形变化和纠错；
- 不新增配置项、构建步骤、下载或语言开关。

非目标：

- 分词词典、WebAssembly、Web Worker，或 Hugo 之外的构建工具；
- 同义词文件；补充同义词仍然用 `search_keywords`；
- 繁体与简体互通；这需要内置一张字表，另行决定；
- 按查询只加载部分索引；只靠 Hugo 的构建无法按词项分片；
- 远端搜索提供者。

## 第一阶段：引擎 {#engine}

引擎不建索引。它把所有可检索的文本拼成一个规整后的字符串，并记下每个页面、
每个小节的每个字段从哪里开始。查询的词项通过扫描这个字符串来定位，
BM25 需要的计数在扫描时一并得到。

### 查询分析 {#analysis}

文本先做 NFKC 规整、转小写、合并空白。查询按输入顺序被拆成片段：

| 片段 | 含义 | 例子 |
| ---- | ---- | ---- |
| 单词 | 用空格分词的文字里的字母或数字 | `port`、`репликация`、`5432` |
| 标识符 | 含 `-`、`.`、`/`、`\`、`_`、`:` 或 `=` 的片段，整体保留 | `shared_buffers`、`--baseURL`、`/pg/data` |
| 符号串 | 两个以上、不含字母数字的字符 | `->>`、`::` |
| 中日韩文本段 | 连续的汉字、平假名、片假名或谚文 | `连接池`、`レプリケーション`、`백업` |

决定类别的是字符的 Unicode 文字系统，页面语言从不参与：英文页面可能引用中文，
读者也可能输入任何一种文字。片段在中日韩字符与字母或数字相邻处断开，
所以 `WAL归档` 与 `WAL 归档` 是同一个查询，`pg_upgrade升级` 是一个标识符加一个文本段。
`文档/搜索.md` 这样的路径仍是一个标识符。

只有一个字符的中日韩文本段是一个词项。更长的文本段变成相互重叠的二元组：
`连接池` 是 `连接` 和 `接池`。没有任何环节判断词在哪里结束。

页面需要覆盖的内容以“格”计数：每个单词、标识符、符号串各算一格，
中日韩文本段的每个字符各算一格。一次查询最多 30 格。

一份很短的英语虚词表和六个中文疑问词照常匹配，但权重只有十分之一，
也不要求页面包含它们。只由这类词组成的查询按原样检索。

### 匹配 {#matching}

每一处匹配要么是精确的，要么是宽松的。

| 片段 | 精确 | 宽松 |
| ---- | ---- | ---- |
| 单词 | 整词 | 以它开头的更长的词；另一种词形；下划线名称中的一段；五个字符以上的词出现在复合词内部；纠错结果 |
| 标识符 | 两侧都不是标识符字符 | 出现在更长的标识符内部 |
| 符号串 | 两侧不是其他运算符字符 | 出现在更长的运算符内部 |
| 中日韩二元组 | 任何出现 | — |

词形变化对 `a`–`z` 的单词使用 Porter 的英语后缀规则。其他字母文字的单词，
开头至少四个字符相同、结尾相差不超过三个字符时视为同一个词。含数字的单词不做词形变化。

拼写帮助只在所选范围内找不到这个词的任何形式时启用。它只处理至少五个字符的
`a`–`z0`–`9` 单词，允许一处编辑，八个字符起允许两处；相邻字符互换算一处。
站点里出现次数最多的三个候选会作为整词检索。标识符从不纠错。

### 排序 {#ranking}

一个页面按权重覆盖了查询至少 90% 的格，就是完整匹配。每一格的权重，
是覆盖它的词项中最常见的那个的逆文档频率。范围内根本不存在的二元组不作要求，
只要它的字符已经被其他二元组覆盖。没有任何词项能覆盖的格保持未覆盖，
此时所有页面都是部分匹配。

页面按以下各项依次排序：

1. 有完整匹配时不显示部分匹配。在一个小节内（连同页面自身的字段）就能覆盖查询的页面，排在需要多个小节才能覆盖的页面之前。
2. 强度。每一格取为它找到的最强匹配：标题 10，关键词 8，标签与分类 6，小节标题 5，描述 3，正文 1；宽松匹配按所在字段的 0.7 计。强度是各格的加权平均；片段按顺序相邻出现时乘以 1.5，再乘以页面的 `search_boost`。
3. 最佳小节的 BM25 得分，乘以 `search_boost`。
4. 标题，然后是 URL。

强度只取决于查询出现在哪里，与出现多少次无关。因此重复只在强度相同的页面之间改变顺序。

部分匹配按覆盖率（以十分之一为档）排序，之后沿用相同的各项，并保留“已匹配/总数”的标注。
标注里一个单词算一个，中日韩文本段按每两个字符算一个。

BM25 以小节为单位，`k1` 为 1.2，`b` 为 0.5，长度按小节的字符数计。
出现次数按字段加权、按匹配质量折算，每个字段最多计 24 次。
长度为 `n` 的文本段，每个二元组的权重是 `n / (2(n − 1))`，因为这一段大约含 `n/2` 个词。

每个页面仍然只占一行，打开的是它的最佳小节。

### 摘要与高亮 {#excerpts}

摘要取最佳小节里展示了最多种命中的 160 个字符。结果带有实际找到的字符串，
所以词形变化和纠错后的拼写会按页面里的写法高亮。单词不会在另一个词的内部被高亮，
除非它本来就能在那里匹配。经过规整的匹配仍然映射回原文。

## 第二阶段：分级加载 {#loading}

索引模板仍然写出带正文的全部文档。Hugo 发布什么，取决于这份输出的大小：

| 索引大小 | 发布的文件 | 正文 |
| -------- | ---------- | ---- |
| 不超过 2 MiB | `offline-search-index.<lang>.json`，与原来逐字节相同 | 在索引内 |
| 超过 2 MiB，正文不超过 8 MiB | 不含 `body` 的索引，加上 `offline-search-body.<lang>.json` | 索引之后自动获取，到达后补入结果 |
| 正文超过 8 MiB，或浏览器要求节省流量 | 同样的两个文件 | 读者选择“搜索正文”时才获取，这一行标明大小 |

2 MiB 就是现有的单个索引原始预算，所以预算之内的站点没有任何变化。
拆分后的索引保留定位页面所需的一切：标题、带锚点和字节偏移的小节标题、
关键词、分类法、描述。正文文件是一组 `{ref, body}` 条目。生产构建中两个文件名都带指纹。

面板仍然在第一次搜索按键时请求索引，并立即显示它的结果。正文加载期间状态行会说明；
此时没有结果，显示的是“正在加载”，不是“未找到”。正文到达后重建引擎，
并保留读者选中的那一行。下载失败时，同一行再次出现供重试。
只打开面板仍然不产生任何请求。

不新增配置项。`offline_search_index` 仍用于手动降级；`summary`、`heading`、`title`
索引没有正文可移。站点覆盖了 `assets/json/offline-search-index.json` 的，同样会被拆分。
字节预算约束的是最先获取的那份索引。

## 第三阶段：可检索条目 {#entries}

参数和函数通常定义在列表里，不是标题，所以原来的索引无法指向它们。
现在索引在标题之外还记录搜索条目：任何带有 `id` 和非空 `data-td-search-entry` 标题的渲染元素。

每个带锚点的参数都是条目，来自 `fields` 短代码的和来自 `{.fields}` 表格的都一样，
不需要任何配置或改写。站点也可以用同样的办法标记自己的元素，通过短代码或区块属性都行。

条目按文档顺序加入 `sections`，字段同样是 `id`、`title` 和 `start`，
所以索引格式和引擎都没有变。正文按这个顺序在标题和条目之间划分：
含有条目的小节只保留第一个条目之前的文字，条目内部的文字命中时打开的是这个条目。
`headings` 仍然只列标题。

`field` 接受 `id`，参考手册因此可以保留已有的锚点，例如用 `guc-work-mem` 而不是 `field-work_mem`。
值不可用，或已被页面上另一个参数使用时，给出告警并保留自动生成的锚点。
与某个标题的 id 相同的情况不会被检测，这一点和任何显式 id 一样。

条目不带类别。目前没有任何地方显示或按类别筛选，这个字段以后可以加进 `sections`，不会破坏读取方。

## 以后的数据库后端 {#backend}

以后的设计可能增加由 PostgreSQL 支撑的搜索提供者。本提案为它保留两点：
索引文件足够完整，可以直接作为语料导入；引擎通过一次调用返回普通的结果行，
面板改为等待结果之后，远端提供者也能给出同样的行。这里不增加任何网络请求。

## 兼容与迁移 {#compatibility}

配置和前言键都不变，2 MiB 以内的索引字段也不变。早期版本写出的索引仍然可以加载。

- 主题不再附带或加载 Lunr，OINK 页面上 `window.lunr` 未定义。使用过主题这份副本的站点需要自行加载。
- `OinkSearchEngine.create` 的参数是 `(documents, maxResults)`，Lunr 参数已移除。
- 结果新增 `marks` 和 `strength`；`score` 与 `textScore` 的数值尺度变了。
- 词项不再匹配短词的内部。依赖 `port` 找到 `support` 的查询，返回的页面会变少。
- 连续短语从一个排序层变为乘数。足够大的 `search_boost` 可以超过它。
- 中日韩文本段不再要求整段出现。原来没有结果的查询，现在可能得到完整或部分匹配。
- 超过 2 MiB 的索引，文档里不再有 `body`。从索引读取正文的工具需要改读 `offline-search-body.<lang>.json`，并按 `ref` 对应。
- 索引被拆分时，对话框多出 `data-td-body-src` 和 `data-td-body-bytes`。`offline-search-index.html` 仍然返回索引的 URL。
- 每个语言包新增两条文案：`ui_search_body_load` 与 `ui_search_body_loading`。
- 渲染出的参数多了 `data-td-search-entry`，索引里每个参数多一个 `sections` 项。含有参数的小节不再代表参数内部的文字，这些文字命中时打开的是参数。

## 接受条件与待定事项 {#acceptance}

主题检查以及本站的 `check` 和 `browser` 目标针对各阶段全部通过，
并且维护者在桌面和手机宽度下审阅过真实中英文内容的结果之后，这些阶段才算接受。
本站的索引在预算之内，所以第二阶段由主题的探针、单元测试和一个更大的消费站点来验证。

待定事项：

1. 权重是否合适？字段分值、宽松系数、短语乘数和 `b` 来自 48 条查询和一部大型手册，不是来自带标注的相关性数据。
2. 完整匹配的页面很少时，是否应该在其后补上部分匹配？
3. `offline_search` 是否默认开启？在维护的站点几乎都设置了它。
4. 繁体与简体是否应该互通？
5. 阿拉伯文和希伯来文的前缀是否需要单独的规则？

## 决策记录 {#decision-log}

- 2026-11-23：起草。实测在 12 MB 文本里每个词项只需 1–8 ms 之后，选择扫描而不是倒排索引。选择二元组，没有采用 `Intl.Segmenter`（它把 `数据库连接池超时` 切成六段，且结果随浏览器变化），也没有采用词典（5 MB，无法随主题分发）。用站点自身文本为查询分词的做法实测不稳定，已放弃。
- 2026-11-23：实现第三阶段。条目只是 `sections` 里多出来的一项，所以索引格式和引擎都没有改。标记是任何元素都能带的一个属性，参数会自己带上。原计划的 `kind` 没有加入，因为没有任何地方会读它。
- 2026-11-23：实现第二阶段。拆分点取现有的 2 MiB 预算，所以合规站点发布的字节不变。索引模板仍是文档的唯一来源，因为有五个消费站点覆盖了它；拆分从它的输出派生。面板打开时不请求正文，以保持“使用命令不产生下载”的规则。
- 2026-11-23：第一阶段在主题工作树中实现。排序从“覆盖查询所需的最弱字段”改为“各字段强度的加权平均”，因为前者让一条回归查询退步。短语从排序层改为乘数，因为它曾把低分的研究页面抬到正式文档之上。
